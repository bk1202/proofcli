# Release procedure

1. Inspect confirmed defects, compatibility changes, and unresolved limits. Update both package version declarations, changelog, and docs; do not infer readiness from test count.
2. Install the hash-locked build tools, build wheel/sdist, run `tools/verify_dist.py`, then run the real-process suite against the installed wheel. `tools/audit_dependencies.py` checks build versions/hashes against PyPI's advisory feed; no runtime dependencies are declared.
3. Only after local validation, publish the candidate branch and obtain green Windows/macOS tests, both distribution-install jobs, and the advisory job. Inspect skips/failures. Merge the same reviewed candidate into main; retain CI links as evidence.
4. Create and push an annotated `v<package-version>` tag targeting the validated commit. A pre-1.0 release is not a production/security certification.
5. The tag triggers `release.yml`. The read-only validation matrix must pass, including Linux runtime and three-platform composite Action checks. The publish job checks tag/version agreement, builds with pinned tools, verifies fresh wheel/sdist installs, installs hash-locked Pillow from `tools/release-requirements.txt` only to draw one PNG from a real failing run and a real passing run, and creates the GitHub release with both distributions, that screenshot, and `SHA256SUMS`. Pillow is not a ProofCLI runtime dependency. The job does not render a demo video.
6. Successful release completion triggers `pypi.yml` on the default branch. Its read-only job accepts only a successful tag-push release from this repository, checks that the tag points to the validated commit, and downloads/checksums the published distribution bytes. A separate `pypi` environment job uses PyPA Trusted Publishing with `id-token: write` to upload those exact bytes. It executes no repository code and stores no long-lived token.
7. Confirm both workflows, actual downloadable checksums, PyPI version metadata, and a fresh `pip install proofcli==<version>` before announcing index availability. Release creation and PyPI publication do not overwrite published versions; inspect partial failures rather than silently replacing bytes.

Before the first PyPI publication, register a pending GitHub publisher at `https://pypi.org/manage/account/publishing/`: project `proofcli`, owner `bk1202`, repository `proofcli`, workflow `pypi.yml`, environment `pypi`. The workflow cannot create that account-level authorization. If registration is missing, complete it and rerun the failed publication job. Pending registration does not reserve a package name.

Actions are pinned to immutable official commits; checkout credentials are not persisted. There is no privileged PR execution or user text interpolated into shell source. Release tags enter shell commands through environment variables. Only GitHub release publication receives repository write permission; only the separate PyPI publication job receives OIDC write permission.

Build-tool locks contain universal wheels and all dependencies needed by supported Python versions. When updating them, review upstream projects/versions, download from PyPI, regenerate hashes, audit advisories, and rerun every platform/package gate. This locks tooling; bit-for-bit reproducible archives across all hosts are not claimed.
